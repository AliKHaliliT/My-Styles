# 0075. Count a record's em dashes from the rule's arrival

Status: Accepted
Date: 2026-09-18

## Context

The em dash budget, two per tracked file, moved into the docs audit on
2026-09-17 so a tree with no remote is held to it, and the record that moved
it gave the count no scope in history. Every other check in this family that
reads history binds from the commit its own scope sentence arrived in, and
the guide says why, since a commit cannot be unmade and a rule that reaches
behind its arrival can never go green. The count reached behind its arrival
into the one class of file that also cannot be edited. A record over the
budget, written before the count ran anywhere but in a workflow, is immutable
beyond its Status line and a link target, superseding it would put a false
entry in the ledger saying the decision changed, and nothing else was
allowed. An upstream entry of 2026-09-18, sent from three seats of one
project at pin 6dab73e5a818, named the gap, with fourteen records over the
budget across four seats, every one older than the rule's arrival there.

## Evidence

The record moving the count into the audit was read; it names every tracked
file and says nothing about history or about records. The guide's sentence
on history-reading checks was read, and it states the principle this record
rests on. The repair clause was read, and it covers a link target alone. The
selftest refuses to run while the unplanted tree is red, which is right,
since a plant proves nothing against a tree that already fails, so a rule a
tree cannot satisfy takes every other rule's proof down with it. Whether a
tracked file is a record is one path test, whether a record was born before
a commit is the ancestry test the audits already make for the filename cap
and the disposition rule, and the family's own trees carry no record over
the budget, so the scope reddens nothing here.

## Options considered

- Exempting records from the count altogether. Refused, because a record
  written after the rule is a tracked byte whose writer can still meet the
  budget, and the count is the one check that catches it at the moment it
  can still be fixed, before the record becomes immutable.
- Superseding a record over the budget. Refused, as the entry argued, since
  a supersession says the decision changed and it did not.
- Widening the repair clause to punctuation. Refused, because the clause
  answers a link that stopped resolving, and a repair of prose is the edit
  immutability exists to forbid.
- Dating the exemption by the record's date line. Refused under the rule
  that history is compared by ancestry and never by the calendar.
- Leaving the count as it was and telling the project to rewrite history.
  Refused; the guide already says a red gate over older commits is a defect
  in the check.

## Decision

The count over records binds from the arrival of its own scope sentence,
like every history-reading check in the family. Every docs audit still
counts every tracked text file, and a file that is a record, one below a
subfolder of docs/, is judged only when it was born in the commit that
brought the scope sentence or after it; a record born before is left to the
history that holds it. The inherited folder is counted where it was written.
Every other tracked file can be edited and is held whatever its age. The
selftest proves that a record over the budget born in the working tree is
reported and that the anchor is the commit that introduced the sentence, and
the rehearsal commits a record over the budget before the audit arrives and
requires the child's audit to pass over it. Under the ladder the rule keeps
its check rung and gains the scope every other history-reading check has.

## Consequences

A project whose records predate the rule goes green on its next
re-alignment with those records untouched, and its selftest runs again. A
record written from now on is held to the budget while it can still be
edited. The audit reads history only when a file is over the budget, so a
clean tree pays nothing new.
