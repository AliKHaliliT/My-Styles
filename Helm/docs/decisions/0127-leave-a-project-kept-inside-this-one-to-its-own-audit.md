# 0127. Leave a project kept inside this one to its own audit

Status: Accepted
Date: 2026-11-21

## Context

The editions document names a project kept inside another, an arrow in
an inquiry or a client beside its server, as a folder that carries a
guide of its own and is cut by its own tool, and the edition tool finds
one by that guide. The docs audit knew no such project. Its checks on
the em dash budget, on invisible characters and on bare citations, and
its vocabulary and spelling advisories, read every tracked file of the
repository, and it told a record from living prose by its place under
the root's own `docs/`. So a client kept in a folder of a server was
read as the server's living prose and configuration, its inherited
records, its copy of the prose law and its audit's selftest among them,
each a file its style carries verbatim and no project may edit. A
project built from the server style met this while adopting the client
style in a folder beside its `app/`, and stopped the adoption there,
since both repairs in its reach were refused, editing files the client's
law carries verbatim and changing the audit the server's law carries
verbatim.

## Evidence

Run on 2026-11-20 at bdb1085, the commit the project's entry pins. A
child of the server style was built as adoption shapes one, and the
client style was copied into a folder of it, its records moved to an
inherited folder of its own and a room drawn for the folder in the
server's map. The server's docs audit failed with eleven findings, each
a record cited by a bare number, nine in the client's inherited records
and two in its selftest, and it advised thirteen times about the
client's files, eleven on vocabulary and two on spelling. Its selftest
stopped at the unplanted tree. These are the entry's counts. With the
client shaped as adoption shapes a child of its own, a twelfth finding
stood, a record of the client's own over the em dash budget, born before
the client's audit arrived. In the same tree the client's own audit and
selftest passed in its folder, and the server's edition tool cut both
projects whole. With the change, the server's audit passes over the same
tree and names the folder it did not read, and both selftests report
every rule firing. The package style's lint was run the next day over a
Python file in a folder kept inside it. It read the file, and judged it
by the folder's own settings where the folder carried them and by the
style's where it carried none.

## Decision

A folder below the root that carries a guide of its own is a project
kept inside this one, anywhere but under the style's own `docs/` and
`edition/`, which hold documents and overlays. It is the sign the
edition tool reads, so the two tools agree on what such a project is.
The outermost such folder is this audit's concern, and a project it
keeps in turn is its own audit's.

The five checks that read every tracked file stop at that folder and
read everything outside it. A folder that carries a guide and no docs
audit of its own fails, because a file this audit leaves alone must be
one another audit reads. The audit's closing line names each folder it
did not read, so a clean verdict hides nothing it left to another. The
folder still needs its room in the map.

The rules of the tree gain the rule. It says the folder is governed by
its own style, gate and conventions, that a change made inside it passes
its gate whatever task asked for it, that nothing is written into it to
satisfy a rule of this project, where its upstream file lives, and that
whoever adopts it adds a job to the root's workflow, since the workflow
the folder carries runs nowhere. It says too what the audit does not
hold. No other command of the gate knows a guide, so the adopter names
the folder in the exclusions of each command that would judge its files
by this project's settings.

The form is a check wherever one decides. The selftest plants a project
with every defect the five checks hold and requires silence, plants the
guide with no audit and requires the failure, plants the same file under
no guide and requires every finding, and plants a guide in the overlay
folder and requires that no project is made of it. The audit was then
broken fifteen ways, and the proofs failed on each. The clauses on
conduct, on the gate's other commands and on the workflow's job are
sentences held in review, as the host's rule on its arrows has been.

## Options considered

- The audit running a nested project's audit and reporting for it was
  refused. A gate runs where it lives, the nested audit may need a
  runtime this project's job never installs, and the host's audit has
  never reached into an arrow.
- A check that the root's workflow carries a job set in the folder was
  left out. It would decide that a job names the folder and not that the
  gate runs. It reopens when a project is found whose nested gate ran
  nowhere while the root's run was green.
- A check that the lint's exclusions name each such folder was left out,
  and so was a rehearsal of a project kept inside one of its own
  language. The case met was a client in a server, two languages no
  command of either gate shares, and a folder with lint settings of its
  own is judged by them. It reopens when a command of an outer gate is
  found judging an inner project's files by the outer settings.
- A list of nested folders declared in the map or the baseline was
  refused, because the guide is already the sign the edition tool reads,
  and a second sign is a second thing to keep true.

## Consequences

A project adopts a second style in a folder and keeps both gates green,
each tracked file read by one audit, and a second style in a repository
of its own stays as open as it was. The family's adoption rehearsal
builds the folder shape, a client child in a folder of a server child,
and runs both gates where they live on every change, so an audit that
reads past a guide fails in the family before it reaches a project. A
guide written into a folder as a note now fails the audit, and the note
belongs in the project's own documents.
