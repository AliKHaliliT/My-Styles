# 0066. Dispose of the entry of 2026-11-19 from a server-style project

Status: Accepted
Date: 2026-11-21

## Context

One project built from the server style holds one upstream entry, dated
2026-11-19 and filed as a defect, pinned at the family's bdb1085, which
the family's history holds. The style's owner pointed the work at the
template, as the reporting rule provides. The project keeps its server
at the repository's root and began adopting the client style in a folder
beside the server's `app/`, the shape the editions document names as a
client beside its server. The server's docs audit read the client's
files as the server's own and failed on files the client's law carries
verbatim, so the adoption stopped. The entry asks which the family
means, an audit that leaves such a project alone or a client that stands
outside the server's root, since the editions document names the nested
shape and no record rules on the audit.

The entry was tested at the pin before ruling. A server child with the
client copied into a folder as the entry describes failed the audit with
the entry's eleven findings and thirteen advisories, and a client shaped
by its own adoption added a twelfth finding. In the same tree the
client's own audit and selftest passed in the folder, and the server's
edition tool cut both projects whole. The docs audit was the one tool
the nested shape had not reached.

## Decision

Kept, and widened to every artifact style.

Two things in the entry are separate. The first is a defect whatever
shape a project takes. In each artifact style the edition tool reads a
folder under a guide of its own as another project, and the docs audit
read the same folder as its own, so one style said two things of one
folder. The audit now agrees with the tool. The second is a choice of
shape with no defect in either, a client in a folder of its server's
repository or in a repository of its own. A repository of its own is the
cleaner separation, with one root, one law and no command to teach. A
folder keeps a server and its client, which change together, in one
clone and one push. The family holds both, and each project chooses.

Treasury 0009 refused the client's source inside the server tree for two
reasons, one tree under two laws and a server that reads what it should
only serve, and its words admit two readings of where that tree ends.
This ruling settles the reading. The server's tree ends at a folder's
guide, as a host's ends at an arrow's, so a folder under a guide of its
own is the client's own tree. Both reasons of that ruling are kept,
since each file stands under one law and the server serves the built
artifact and reads no source. The client's source under no guide of its
own, anywhere below the server's root, stays refused.

The docs audit of every artifact style now leaves a folder that carries
a guide of its own to that project's audit, fails such a folder that
carries no docs audit, and names each folder it did not read. The rules
of the tree in the three artifact styles say so, with who answers for a
change made inside such a project, where its gate runs on a hosted
runner, and what the audit does not hold, the gate's other commands,
which the adopter keeps out of the folder. The host changes nothing,
since its audit skips its arrows by path and its rules already hold the
split. The package seat's 0131, the server seat's 0137 and the client
seat's 0127.

## Options considered

- Requiring a client to stand in a repository of its own was refused as
  the only shape. It stays open to every project, and it was not made
  the rule because the host has kept projects in folders under their own
  guides since it was built, and one repository is how a product with
  two halves is cloned, changed and pushed.
- A root that belongs to neither, with the server and the client in
  folders side by side, was refused. Such a root carries no guide, so no
  law binds it, no audit reads it, no tool cuts its edition and its
  workflow answers to no style. It reopens when a project needs two
  products of equal standing in one repository.
- Holding the gate's other commands out of the folder by a check, and
  the workflow's job by another, was left to the seats' records, which
  say what reopens each.
- Moving the host's audit from its path to the guide was not done. The
  host's rules name `arrows/` as where its projects live, nothing in a
  host has met the difference, and a change there would be a change no
  entry asked for.

## Consequences

The project deletes the entry at its next re-alignment, takes the audit,
and adopts the client with a room in its map and a job in its workflow.
The family's adoption rehearsal builds a client child in a folder of a
server child on every change and runs both gates where they live. A
reader of treasury 0009 who meets a client under a server's root finds
here why it stands.
